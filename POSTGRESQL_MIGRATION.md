# Crew Center PostgreSQL migration

This repository prepares the application for PostgreSQL. No production
database, Aiven service, Vercel setting or deployment is changed by this work.
The final data transfer and cutover are separate operator actions after the
rehearsal passes.

## 1. Rehearse in an empty database

Keep MySQL available. Take a complete schema-and-data backup and record the
actual tables, columns, constraints, row counts, service size, collation and
timezone behavior. Compare the backup with the application's models and
historical migrations; the files alone cannot prove what production contains.

Create an empty PostgreSQL database for the rehearsal. Use provider TLS and
its CA certificate for hosted connections. With a connection configured in
`CREW_TEST_DATABASE_URL`, apply the baseline:

```sh
psql "$CREW_TEST_DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/postgresql/001_baseline.sql
```

The baseline deliberately fails if tables already exist, and wraps creation
in a transaction. It needs no PostgreSQL extensions. It creates all 24 tables
used by the models and database helpers. The unused `news` model also has a
table; preserve its data if the source database contains any. Do not run the
historical MySQL files on PostgreSQL or use automatic schema synchronization
against an imported database.

## 2. Map and restore the data

Prepare explicit column lists for each table. Use a reviewed conversion or
CSV export/import into the baseline, rather than applying a MySQL dump as
PostgreSQL SQL. Preserve NULL versus empty string, Unicode, JSON, IDs, password
hashes and encrypted token text. Import parent tables before their referencing
tables, following the order in the baseline. Do not disable constraints to
hide import failures; reconcile conflicting rows before accepting the result.

| Source data | PostgreSQL mapping |
| --- | --- |
| Auto-increment IDs | Existing integer IDs imported explicitly into `GENERATED BY DEFAULT AS IDENTITY` columns |
| `pilots.status`, aircraft/PIREP status, `applications.exam_status`, `awards.featured` | Integers, including values beyond `0` and `1`; do not cast every tinyint to boolean |
| `live_aircraft.active`, `tokens.isRevoked` | Booleans; explicitly map only source `0`/`1` to `false`/`true` and investigate any other value |
| `pireps.date`, `awards_granted.dateawarded` | `DATE`, keeping the same `YYYY-MM-DD` calendar date |
| MySQL `DATETIME`/timestamps | `TIMESTAMPTZ`; establish the source timezone before conversion and preserve the instant in UTC, including milliseconds where present |
| Cache `expires_at` | Integer epoch milliseconds, without timezone conversion or TTL extension |
| `criteria`, event `details`, `last_published_payload` | JSON, keeping SQL NULL distinct from JSON `null` |

Confirm every imported identity fits PostgreSQL's signed 32-bit integer range;
the former unsigned OTP identity must be checked rather than silently truncated.

Authentication columns retain their exact spelling. Quote
`tokens."pilotId"`, `"expiresAt"`, `"createdAt"`, `"updatedAt"`, `"isRevoked"`,
and `otps."createdAt"`/`"updatedAt"` in import column lists. Never let an import
tool silently lowercase them. The live MySQL token table uses `token` as its
primary key and has no `id` column. Preserve every source token and let the
PostgreSQL identity generate the new internal IDs; there are no incoming token
ID references to remap. Existing bcrypt password hashes need no
rehashing. Keep the current `JWT_SECRET` and `IF_LIVE_TOKEN_ENCRYPTION_KEY`, plus
the existing IF OAuth configuration, so copied sessions and encrypted IF
credentials remain usable.

Audit case variants in email and IFC usernames before transfer. Login and
identity matching must retain case-insensitive behavior when moving away from
the source MySQL collation. Report duplicate normalized identities for review;
do not merge pilots or renumber IDs. Preserve displayed IFC username casing.
Check uppercase/lowercase searches as well as existing mixed-case email login
and password resets.

The operator tools `scripts/migrate-mysql-to-postgres.mjs` and
`scripts/import-mysql-snapshot.mjs` use private connection files and explicit
commands. Keep connection details and backups under the ignored `.migration/`
directory with restricted file permissions. The export preserves a read-only
snapshot with schema metadata, counts and file hashes. The importer rehearses
inside a transaction and rolls back unless `--commit` is supplied; it verifies
the imported source columns before committing. Use its explicit expired-cache
option to leave expired cache rows out without changing any remaining TTL.

The baseline seeds `options.live_scheduling_mutex`. If restoring the entire
source `options` table, first empty this target table, restore the source rows,
then ensure the required row exists:

```sql
INSERT INTO options (name, value) VALUES ('live_scheduling_mutex', '1')
ON CONFLICT (name) DO NOTHING;
```

Preserve aircraft bindings, flight revisions, queue positions, current
publishing state and outbox jobs. A migration must not replay pending or
uncertain IF writes. Do not extend cache lifetimes; expired cache entries and
fetched IF responses need not be transferred. Preserve unexpired rate-limit
counter expiry times if those counters are restored.

## 3. Reset and verify ID sequences

After all explicit IDs are imported, with application writes stopped:

```sh
psql "$CREW_TEST_DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/postgresql/002_reset_identity_sequences.sql
```

This sets each identity sequence so its next generated value is above the
largest imported ID; an empty table starts at `1`. It does not change any
existing ID. Compare per-table row counts, min/max IDs and ID sets with the
backup. Also compare approved PIREP counts and flight-second sums per pilot,
award grants, permissions, applications, notifications and scheduling queues.
Verify there are no broken references or duplicate grant/queue keys.

On the rehearsal copy, create a representative new pilot, PIREP, token and
flight using generated IDs and verify they do not collide. Inspect their
referenced IDs and date/time values, then discard the rehearsal copy. Repeat
the sequence reset and checks after the final import. A sequence reset alone
does not prove that the data import was complete.

## 4. Verify application behavior and connection usage

Run the normal tests, type check, lint and production build. Opt-in database
tests must use a dedicated `postgres://` or `postgresql://` database named
`webncrew_scheduling_test_<name>`, never the production connection. Run the
database suites serially; they create and remove only their isolated test
schemas. The test setup enables non-TLS connections only for local testing.

Before starting a restored application, disable or mock **all** external
integrations, including IF reads, writes and OAuth refresh/revocation, Brevo
email and Discord webhooks. Use isolated test credentials or mocked fixtures;
do not let copied production credentials reach those services. An IF preview
organization or disabled publishing flag alone is insufficient: refreshing a
copied rotating OAuth token can invalidate the production token even without
publishing a flight. Ensure background callbacks use these same isolated
integrations.

Exercise existing login/session/logout, password reset and its rate limits,
signup duplicate checks, PIREP filing/review/search, awards, notification reads,
admin reports, route imports and IFC/award scripts on the restored copy. Check
date-only fields around midnight and timestamp fields around a DST boundary.
Use the mocked integrations throughout rehearsal; the test copy must not make
live provider calls, send mail or post webhooks.

Scheduling tests must demonstrate that publishing, matching and editing the
same aircraft cannot overlap; competing pilot/aircraft bookings remain safe;
other aircraft can progress; transaction errors release advisory locks; and
uncertain IF writes still require reconciliation. The advisory lock uses a
dedicated transaction; local checkpoint transactions must remain short, with
no aircraft/pilot/mutex row locks held over IF network requests.

Aiven free PostgreSQL has a service-wide budget of 20 connections. The app's
`DB_POOL_MAX` defaults to `3` per process, with a minimum of `2`, and the pool
keeps no minimum idle connections. Vercel processes, preview deployments,
scripts, tests and operator sessions all share the service limit. A small
per-process pool does not impose a global cap. Measure representative combined
traffic and simultaneous scheduling operations, including deployment overlap;
require spare connections and no acquisition stalls before accepting cutover.
Do not point preview deployments at production during this test.

## 5. Later production cutover

1. Pause **all database-backed application traffic**, including GET endpoints,
   old deployments, scripts, admin sessions and background callbacks; GET
   requests can perform cleanup or OAuth refresh writes. Stop IF publishing,
   wait for in-flight requests/publishers to finish and review uncertain outbox
   jobs before taking the final snapshot. Keep the old database available.
2. Take the final MySQL backup, restore it to the prepared PostgreSQL target
   using the rehearsed mappings, reset identity sequences, and repeat the data
   comparisons. Confirm the mutex option and connection budget.
3. Deploy the matching PostgreSQL code with the new `DB_*` connection values,
   provider CA and existing auth/encryption keys. Confirm the old deployment
   cannot keep accepting traffic. Keep public traffic closed for smoke tests.
4. Verify login, existing sessions, historical data, a new record and scheduling
   state. Reopen writes only after those checks pass. Re-enable IF publishing
   deliberately after reviewing queued and uncertain jobs.
5. Retain the MySQL backup and old code until the PostgreSQL deployment has
   been verified under real use. A simple rollback is available only before
   the new application makes PostgreSQL writes **or external side effects**,
   including OAuth refresh. Smoke tests can cross this boundary. After any
   such activity, pause traffic and reconcile records and rotating credentials
   before reverting code/config; an OAuth reconnect may be needed. Switching
   databases alone would lose new records or restore stale provider tokens.
